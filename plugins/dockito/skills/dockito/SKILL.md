# Dockito

Dockito hosts Markdown and HTML docs, live sheets, Slides, boards, API docs and database designs, at a short link, with History. The `dockito` CLI publishes, syncs, reads and restores them.

Before the first Dockito command in a conversation, run `dockito agent`: it says what Dockito is and how to use the CLI, from the version installed, so it is always current. `dockito <command> --help` explains each command.

What matters most:
- Run `dockito tree` before putting a doc anywhere. When a doc belongs in a project, ask the user where; never guess. Pass `--to` every time: the CLI remembers nothing.
- Docs are private. Add `--public` only when the user asked for a public link.
- To change part of a published Markdown or HTML doc, use `dockito edit <doc> edits.json --base N` (exact text, only what changes), not a whole new publish. N is the entry `dockito get` says. Finds match the file as stored: for HTML its source, not the readable text of `get --text`.
- Comments: `dockito comments <doc>` lists open threads in reading order, each by ID and where it sits; `dockito get <comment link>` reads one. `dockito comment <doc> "text"` starts a thread (`--on "exact text"`, `--box s3.b2`, `--item s4`), `--thread <id>` replies, `--resolve` closes it. "@Name" tells someone. The user needs Comment or Edit on the doc.
- Approvals: `dockito approvals <doc>` shows the open request (each approver's answer, "outdated" when the doc changed after) and history. `dockito request-approval <doc> --to "@Mia, @Max"` asks (`--message`, `--due yyyy-mm-dd`, `--lock`: no changes until decided), `--cancel` withdraws; `dockito approve <doc> --base <n>` or `dockito reject <doc> --base <n> --reason "…"` answers on the version you read (`approvals` says it), only ever the latest: `doc_changed` means read it again. Asking keeps that version as a saved point in History. A locked doc refuses every change (`locked`); comments still work.
- Use `--json`. Exit code 2 means the CLI needs a choice: show the user the choices it lists and run the one they pick.

Slides are live decks people and agents edit together. Make one by publishing a slide-shaped .html: `<html data-theme="Harbor">`, one `<section>` per slide, every element a box with a class and left/top/width/height in px; pictures beside the file go with it. Before your first deck, `dockito kit [theme]` gives the theme's classes and example slides (`dockito get <deck> --kit` for a deck's). Then change it with `dockito edit-slides`, never by publishing again. People select boxes and ask the AI: `dockito asks <deck> --watch` prints each ask as a line of JSON; answer it with `dockito edit-slides` and "answers": "<ask id>".

Boards are live whiteboards people and agents edit together; publishing a .canvas (JSON Canvas) makes a new one; `dockito publish Retro.canvas --template 4ls` starts one from a template (start-stop-continue, 4ls, mad-sad-glad, brainstorm, workshop, design-sprint). `dockito get <board>` gives the table of contents and version, `--frame f2` a frame's items by short ID. Change it with `dockito edit-board <board> ops.json --base N`, never by publishing again: `cluster` groups stickies (you pick the groups, Dockito lays them out). `dockito asks <board> --watch` prints what people ask the AI, one line each; answer with "answers": "a3" in the edit.

Word docs: `dockito get <doc>` gives the outline (headings with IDs and pages) and version; read only what a change needs (`--blocks h3`, `--pages 4-6`, `--find "fees"`), then send every change in one `dockito edit-word <doc> ops.json --base N` by block ID: up to 500 ops, all or none (`dockito edit-word --help` lists them). Edits land as suggestions people accept or reject, unless the doc says AI changes: Edit directly. `dockito asks <doc>` lists what people asked about selected text; answer with "answers".

API docs: `dockito publish openapi.yaml` makes or updates an API doc from an OpenAPI 3.x file, and says what changed and what breaks. `dockito get <doc>` gives its overview and version; `--find "create a buyer"` names the operations for a task, then `--ops`, `--schemas`, `--types` or `--call` read just those, never the whole file. `dockito check <doc>` runs the checks on the published one. `dockito check openapi.yaml --against <doc>` checks a local spec and compares it with the published one (exit 1 errors, 2 differs, 3 breaking; `--format markdown` for a PR comment). `dockito changes <doc>` lists what the last version changed, breaking first. `dockito pull <doc> --as postman` exports it (json, yaml, md, postman).

Database designs are DBML schemas people and agents edit together, drawn as a diagram; publishing a .dbml or .sql file makes one, and publishing it again the next version (the file as the whole schema). `dockito get <design>` gives the DBML (the outline past 80 tables) and version; `--db '{"tables":["orders"],"hops":1}'` reads part. Change it with `dockito edit-db <design> ops.json --base N`: all or none, and the reply ends with the checks it touched, each with a fix op. `dockito check <design>` exits 1 on errors; `dockito check schema.dbml` checks a local file without sending it, `--doc <design>` also compares (exit 2 when they differ). `dockito changes <design> --since N` gives what changed and the migration SQL. `dockito pull <design>` writes it to schema.dbml (`--sql postgres|mysql` for SQL) for the repo; publishing that file back makes the next version.

This plugin also connects Dockito's MCP server: when the `dockito` CLI isn't installed, use the Dockito MCP tools instead (same docs, same access). The CLI is better for files on this machine and folders of docs; to get it, ask the user to install it with `brew install dockito-ai/tap/dockito`. If it says not logged in, ask the user to run `dockito login`, which opens their browser. With several logins (`dockito accounts`), `--account <email>` or DOCKITO_ACCOUNT picks one.
